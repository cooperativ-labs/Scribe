# Focused-field AX feasibility matrix (macOS 27)

> Historical report: `DictationFeasibility` was retired in coo:1071. Its commands below
> describe the original run. See [maintained tools and coverage](../../Tools/README.md).

## Method and scope

The Developer ID signed, unsandboxed throwaway probe in `Tools/DictationFeasibility` ran as an app after the user enabled it in macOS 27's **Device Control and Data Access** pane. `AXIsProcessTrusted()` and `CGPreflightPostEventAccess()` then returned true. Its one-shot AX checks record only app name, role, error codes, geometry, value length and insertion success flags; they do not log field contents. It uses a 250 ms messaging timeout on the system-wide element and focused element, with a 1-second diagnostic retry.

`AXUIElementCreateSystemWide()` → `kAXFocusedUIElementAttribute` often returned **`kAXErrorCannotComplete` (−25204)**, including with Safari and Chrome frontmost; an app-specific `AXUIElementCreateApplication(frontmost PID)` query then resolved the field. Explicit activation from the signed probe made the system-wide query succeed for Mail, Cursor, Xcode and Terminal. The production locator needs both paths and a timeout. Electron's [documented `AXManualAccessibility` setting](https://www.electronjs.org/docs/latest/tutorial/accessibility) was needed on this machine before Slack and Cursor exposed their editors. The user approved that setting for these tests; it returned success, and the tree became available on a subsequent probe launch. The probe set it back to false in both apps after testing (both calls returned success).

For TextEdit the focused element's AX frame was `(x: −3340, y: −346, width: 656, height: 384)` and the zero-length selection's `AXBoundsForRange` returned a caret at `(x: −3330, y: −359, width: 0, height: 13)`. The focused window's frame was also available. This is a multi-display coordinate space with negative positions. The probe's AppKit conversion used `NSScreen.screens.first.frame.maxY − axRect.maxY` for the bottom-left `y`; it returned `y: 1662` for that caret. Placement code must then choose the target screen and clamp to its visible frame. A zero-width caret rect is usable as an anchor.

## Test limitation and design implication

TextEdit, Notes and Xcode validate the proposal's direct AX strategy for native text views and its read-back requirement. Notes initially returned −25212 for `AXValue` in an empty note, but after direct AX insertion its value contained the token. Safari, Chrome, Cursor and Slack demonstrate why `AXSelectedText` being reported settable and returning success are insufficient: only the `AXValue` read-back revealed a no-op, while posted Cmd-V inserted the token. Mail's unsent compose body exposed `AXWebArea` as the focused element, with no selection range; posted paste worked, but the token was present in a descendant's AX value rather than the root web area's value. Chrome's contenteditable, Slack and Terminal returned formally successful but all-zero caret rectangles. Cursor returned a useful caret rectangle but a tiny 1×17 px focused element frame. Chrome initially returned −25212 (no focused UI element) until the user selected the correct tab and field; requesting `AXEnhancedUserInterface` returned −25208, so the probe did not establish that that request enabled access. [Chromium's accessibility documentation](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/accessibility/overview.md) says renderer accessibility may be enabled on demand. The computer-control service timed out, so the user focused disposable fields and the signed probe explicitly activated named apps for one-shot checks. A 15-minute combined AX/keyboard capture was rejected by automatic UI review because it could inspect changing focused fields; the one-shot, field-scoped probe above was the safer method used instead.

Section 8 of `docs/proposals/dictation.md` should add an app-specific focused-element query using the **frontmost PID** when the system-wide query returns −25204, with the same timeout and PID/focus revalidation before insertion. It should require value read-back after direct AX insertion and fall back to paste on a no-op such as the tested Safari, Chrome, Cursor, and Slack fields. It should reject zero or off-screen caret rectangles even when `AXBoundsForRange` reports success, and use a window fallback when an element frame is merely a tiny hidden input, as in Cursor. Electron apps may need an `AXManualAccessibility` request before their editor tree is exposed; the user explicitly approved that change for this spike. VS Code was replaced by Cursor at the user's request; a Java app needs another machine or installation.
